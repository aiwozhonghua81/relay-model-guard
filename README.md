# 中转 API 模型检测器（Relay Model Guard）

给任意 OpenAI 兼容中转 / 代理端点做一次「体检」：填 `base_url`、`api_key`、声称的模型名，后端并发跑 14 个探针，每个探针给出 **0–10 分 + 状态 + 一句证据 + 耗时**，再按权重汇总总分与风险等级。前端卡片网格实时刷新，可展开看原始证据，最后导出 JSON / HTML 报告。

> 📖 **产品介绍、界面说明、结果解读、API 用法、FAQ** → [docs/GUIDE.md](docs/GUIDE.md)

> ⚠️ **使用前必读**：[免责声明](DISCLAIMER.md) —— 本工具会向目标端点发送真实请求、消耗其额度，并可能触发对方风控；请**只用于你已获得授权的端点**，并使用独立的测试密钥。

## 运行

```bash
node server.mjs            # 或 npm start  → http://127.0.0.1:8787
node mock-upstream.mjs     # 可选：本地演示桩 → http://127.0.0.1:8788/v1
node scripts/selftest.mjs  # 端到端自测（起假上游 + 跑完整检测 + 断言）
npm run audit              # 开源前的脱敏体检（密钥 / 绝对路径 / 邮箱 / 本机用户名）
npm run publish:github     # 一键建仓库并推送（需先安装并登录 gh CLI）
```

零依赖，只要 Node ≥ 18（用到内置 `fetch` 与 Web Streams）。默认只监听 `127.0.0.1`。

### 本地演示

先启动演示桩，再打开应用，用「本地演示桩」快速填充：

- **诚实模式**：API Key 随便填（如 `demo-key`），模型 `gpt-4o-mini` → 总分通常 9 分以上。
- **黑心模式**：API Key 或模型名里带 `shady`（如 `shady-demo-key`）→ 演示桩会同时作弊：调包成 `llama-3.1-8b-instruct`、隐藏系统提示词、忽略 `max_tokens`、越狱直接吐口令、错误堆栈泄露、上下文静默截断、吞掉 tool_calls、特殊 token 注入生效……总分掉到 4 分以下。

## 14 个探针与权重

| # | 探针 | 权重 | 分组 | 检什么 |
|---|------|------|------|--------|
| 1 | 连通性检查 | 10% | 基础 | 端点可达、鉴权有效、`/models` 是否含声明模型 |
| 2 | 延迟信号 | 7% | 基础 | 首字延迟、生成吞吐、是否被网关整体缓冲 |
| 3 | 流完整性 | 6% | 基础 | SSE 结构：增量、`delta.role`、`finish_reason`、`[DONE]`、流式 `usage` |
| 4 | 模型身份 | 9% | 一致性 | 模型自述的标识 / 开发者 / 知识截止是否与声称一致 |
| 5 | 模型调包 | 10% | 一致性 | 响应 `model` 字段 + 3 道能力基准题（含陷阱题） |
| 6 | 渠道指纹 | 7% | 溯源 | 响应头特征（OpenAI 原生 / Azure / CF / 火山 / new-api 等）与错误体标识 |
| 7 | Token 注入 | 6% | 安全 | 注入 ChatML / `[INST]` 等特殊标记，看是否被当真实角色执行 |
| 8 | 提示词提取 | 7% | 安全 | 能否回读系统提示词，是否夹带隐瞒、计费、品牌注入 |
| 9 | 指令覆盖 | 7% | 安全 | 用户文档里埋的指令能否劫持系统级约束 |
| 10 | 越狱抵抗 | 7% | 安全 | 用自持口令 + 3 种话术，测是否被换成无限制模型 |
| 11 | 错误泄露 | 5% | 安全 | 非法请求的报错是否泄露堆栈、路径、密钥、内网地址、真实上游 |
| 12 | 上下文截断 | 6% | 能力 | 长输入埋点，检测静默截断 / 裁剪（并用 `usage` 交叉验证） |
| 13 | 工具篡改 | 6% | 能力 | 函数调用链路是否被改写：schema、参数、`function.name` 一致性 |
| 14 | 钱包安全 | 7% | 计费 | `usage` 真实性、`max_tokens` 是否生效、重复请求缓存命中却照价计费 |

总分 = Σ(权重 × 得分) / Σ(已执行权重)，10 分制。风险等级：≥9 极低 / ≥8 低 / ≥6.5 中等 / ≥5 较高 / ≥3 高 / <3 极高。

## Token 预算保护（两道闸门）

检测一次要打 30 多次上游请求，最贵的「上下文截断」探针就占九成消耗，所以做了两层防护，避免把额度跑爆。

**第一道：启动前预估 + 源头拦截**

服务启动时会把 14 个探针**干跑一遍**（纯本地计算，不联网、不发任何请求），按 `prompt 估算 + 输出长度` 算出整套检测的 token 预估。每次提交检测时：

- 预估 > 你设置的上限 → **直接拒绝启动**，返回 `400 BUDGET_TOO_SMALL`，**一个请求都不会发给端点**，同时给出提高上限的具体数值、调小 `LONG_CONTEXT_CHARS` 等建议。
- 预估 ≥ 上限的 70% → 放行但前置告警（页面黄色提示 + `202` 响应里的 `warning` 字段）。
- 前端同步做同样的校验：预估不达标时「开始检测」按钮直接置灰，附上拦截原因。

预估值 = `预期消耗 × TOKEN_ESTIMATE_SAFETY`（默认 1.15）。接口里同时给出 `expectedTokens`（预期）与 `worstCaseTokens`（每个请求都把 `max_tokens` 用满）。可以用勾选「额度不足时仍运行」显式放行，此时会退化为第二道闸门的「跑到触顶为止」模式。

**第二道：运行时闸门（硬上限）**

- 每个请求**发送前**先预占额度（prompt 估算 + 该请求的 `max_tokens`）；预占后会超上限的请求**不会被发出**。
- 请求返回后用响应里的真实 `usage` 结算；拿不到 `usage` 就按预占值保守记账。
- 累计用量触顶 → 立刻 `abort` 掉所有在途 fetch / 流式读取，剩余探针不再执行，**重试循环也不会再发新请求**。
- 触顶的探针标记为「已终止 / 已跳过」，**不参与总分计算**（避免把我们自己的额度策略算成端点的问题）；全部探针都没跑出结果时给「检测未完成」结论而不是 0 分。
- 另有总时长护栏 `RUN_DEADLINE_MS`（默认 5 分钟），避免并发探针卡在重试里空转。

界面上的实时用量条会随 SSE 的 `usage` 事件刷新（`已用 / 上限`，并显示在途预留）；报告里也会带上本次用量的 `spent / limit / usedPercent`。

## 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/catalog` | 探针目录、权重、并发/超时配置，以及整套检测的 `estimate` 预估 |
| `POST` | `/api/detect` | `{ baseUrl, apiKey, model, tokenBudget, allowPartialRun }` → `202 { runId, estimate, warning }`；预估超上限时返回 `400 BUDGET_TOO_SMALL` |
| `GET` | `/api/detect/:id/events` | SSE：`probe-start` / `probe` / `usage` / `summary` / `done` 事件流 |
| `GET` | `/api/detect/:id` | 当前快照（断线重连用） |
| `GET` | `/api/detect/:id/report.json` | 下载 JSON 报告 |
| `GET` | `/api/detect/:id/report.html` | HTML 报告（加 `?download=1` 变下载） |
| `GET` | `/api/health` | 健康检查 |

## 安全设计

- **API Key 只走内存**：`run` 对象持有密钥，14 个探针跑完立刻置 `null`；进程不写任何数据库、文件、缓存。检测记录本身也只在内存里保留 30 分钟（`RUN_TTL_MS`），`SIGINT/SIGTERM` 时清空。
- **日志脱敏**：所有控制台输出统一过 `safeLog()` → `redact()`，命中 `sk-*`、`Bearer *`、`api_key=`、长随机串等模式一律打码；只打印 Key 的不可逆指纹（8+8 hex）用于区分。
- **报告不含密钥**：SSE 与报告走 `publicRun()` 白名单序列化，`authorization` 类字段被强制替换为 `***REDACTED***`，请求体、响应头也都会过一遍 `redact()`。
- **前端即弃**：检测发起后立刻清空输入框里的 Key，页面不再持有。
- **服务默认只听 127.0.0.1**；限流 40 次 / 10 分钟 / IP；请求体上限 32 KB。

> ⚠️ 本工具会按你提供的 `base_url` 发起出站请求。**无鉴权时不要暴露到公网**（否则等于开放一个能读回响应的 SSRF 代理）。要放到服务器上，请用下面的 deploy-safe 模式。

## 部署到服务器（deploy-safe 模式）

本地模式（默认）没有鉴权、允许私网目标，只适合跑在自己机器上。要放到服务器/内网时用：

```bash
# macOS / Linux
DEPLOY_SAFE=1 APP_TOKEN="$(openssl rand -hex 24)" node server.mjs

# Windows PowerShell
$env:DEPLOY_SAFE="1"; $env:APP_TOKEN="用上面命令生成的随机串"; node server.mjs
```

打开页面先填写 `APP_TOKEN` 登录，之后 12 小时内免登录（会话 Cookie 为 HttpOnly + SameSite=Strict）。`DEPLOY_SAFE=1` 但没给 `APP_TOKEN` 会**拒绝启动**，避免"以为开了防护其实没有"。

deploy-safe 开启后：

| 能力 | 行为 |
|---|---|
| 鉴权 | 所有 `/api/*` 需要令牌（`/api/health` 与 `/api/session` 除外）；支持页面登录、`Authorization: Bearer`、`x-app-token` 三种方式；登录接口单独限流 10 次/10 分钟 |
| SSRF 防护 | `base_url` 解析出的**任意一个** IP 落在私有/回环/链路本地/组播/保留段（含 `169.254.169.254` 云元数据、`::1`、`fc00::/7`）就拒绝启动检测，一个请求都不发 |
| 重定向 | 改为手动逐跳跟随（默认最多 3 跳），**每一跳都重新校验目标**，防止"先跳到自己域名再 302 进内网" |
| 全局配额 | 默认每小时最多 60 次检测、同时最多 2 个检测在进行中（超了返回 429） |
| 反向代理 | 设置 `TRUST_PROXY=1` 后，限流按 `X-Forwarded-For` 第一跳计；HTTPS 反代下会话 Cookie 自动加 `Secure` |

想在内网服务器上继续检测本机/内网端点（例如自建的演示桩），显式设置 `ALLOW_PRIVATE_TARGETS=1` 放行——启动日志会明确警告"SSRF 防护已关闭"。**不要同时暴露到公网。**

> 已知边界：目标校验发生在发请求之前，理论上存在 DNS rebinding 的 TOCTOU 竞态窗口；deploy-safe 已用"鉴权 + 全局配额 + 逐跳校验"三层兜底。若面向不受信任的用户开放，请再配一层出站防火墙策略。

## 可调参数（环境变量）

| 变量 | 默认 | 说明 |
|------|------|------|
| `PORT` / `HOST` | `8787` / `127.0.0.1` | 监听地址 |
| `PROBE_CONCURRENCY` | `3` | 探针并发度（1–14）。默认取保守值以免撞上中转限流，需要更快可调高 |
| `PROBE_TIMEOUT_MS` | `75000` | 单个探针超时 |
| `RUN_TTL_MS` | `1800000` | 内存中检测记录保留时长 |
| `LONG_CONTEXT_CHARS` | `32000` | 上下文探针的长输入长度（≈9k token） |
| `TOKEN_BUDGET` | 按预估自动算 | 默认 Token 上限；留空时自动取 `预估 × 1.15`（当前约 39k） |
| `TOKEN_ESTIMATE_SAFETY` | `1.15` | 前置闸门安全系数：`预估 = 预期消耗 × 系数` |
| `RUN_DEADLINE_MS` | `300000` | 单次检测总时长护栏，到点中止所有探针 |
| `DEPLOY_SAFE` | `0` | 设为 `1` 开启部署安全模式（鉴权 + 私网拦截 + 全局配额） |
| `APP_TOKEN` | 无 | deploy-safe 下的访问令牌；`DEPLOY_SAFE=1` 时必填，否则拒绝启动 |
| `ALLOW_PRIVATE_TARGETS` | 本地 `1` / deploy-safe `0` | 是否允许请求私网/回环/链路本地地址 |
| `MAX_REDIRECTS` | `3` | 手动跟随重定向的最大跳数（每跳都校验目标） |
| `GLOBAL_RUNS_PER_HOUR` | 本地 `0`（不限）/ deploy-safe `60` | 全局每小时检测次数上限 |
| `MAX_CONCURRENT_RUNS` | 本地 `10` / deploy-safe `2` | 同时进行的检测数上限 |
| `SESSION_TTL_MS` | `43200000` | 登录会话有效期（12 小时） |
| `TRUST_PROXY` | `0` | 置于反向代理后时设为 `1`，按 `X-Forwarded-For` 限流 |

## 结果怎么读

- **分数不是判决书**：`模型身份`、`模型调包`、`越狱抵抗` 依赖模型自述与行为，属概率性证据；`连通性`、`流完整性`、`错误泄露`、`工具篡改`、`钱包安全` 属确定性证据，优先级更高。
- **单点异常先看证据**：每张卡片都能展开原始请求/响应（请求体、响应头、SSE 样本行、usage），先确认是不是自己的网络或模型名写错。
- **常见组合**：`调包 + 身份冲突 + 指纹混浊` 一般意味着二次转售；`流完整 + 便宜但缓存命中` 常见于共享池；`Token 注入 + 访问日志异常` 说明网关做了裸文本拼接。


## 已知边界

- 只支持 OpenAI 兼容协议（`/chat/completions`、`/models`）；Anthropic 原生 `/v1/messages` 未适配。
- 上下文探针会真的发送约 9k token 的长输入，会产生实际费用；改小 `LONG_CONTEXT_CHARS` 可降低成本。
- `usage` 的「真实性」只能与字符级估算做量级比对，不能精确到 token；结论会写成区间判断。
- 探针并发默认 3（可调到 14）+ 抖动，仍可能触发严格限流的中转；遇到 429 会自动重试 2 次。
- **预估偏保守**：预估值按「每个分支都真的发出请求」的最坏剧本统计（含 `/models` 失败时的补 ping、`stream_options` 不被支持时的重试等），且中文按 0.8 token/字估算，通常高于实际消耗（实测诚实端点约 1 万 token，预估约 3 万）。它的职责是拦住「明显会跑爆额度」的提交，真实消耗以运行时闸门结算的 `spent` 为准。
- **预估依赖探针实现**：预估值由干跑产生，改了探针提示词/长度会自动跟着变，不需要维护常量表；若某次运行中端点触发额外的重试/重放，实际消耗可能超过预估，这种情况由运行时闸门兜底。
